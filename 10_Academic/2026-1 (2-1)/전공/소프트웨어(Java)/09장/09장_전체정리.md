# 9장. Class 기본 (2) — 전체정리

> 8장에서 class의 기본 골격(필드 + 메소드 + 생성자)을 봤다면, 이 장은 **"왜 객체지향으로 짜는가"**와 **"data를 어떻게 보호하는가(접근 지정자·캡슐화)"**가 핵심이다. 객체를 메소드에 넘기고 배열로 다루는 실전 감각도 같이 잡는다.

## 1. 왜 객체지향 설계인가 (자판기 예제)

자동판매기를 설계한다고 하자. 똑같은 문제를 두 방식으로 풀 수 있다.

- **Procedure-oriented Design**: "동전을 넣는다 → 버튼을 누른다 → 음료가 나온다"처럼 **기능(동작) 중심**으로 쪼갠다. 함수가 주인공.
- **Object-oriented Design**: "자판기"라는 **object**를 중심에 두고, 그 안에 상태(잔액, 재고)와 동작(insertCoin, selectItem)을 함께 둔다.

> 둘 다 되는데, 어느 게 더 **자연스럽고 관리가 쉬운가**?

여기서 교수님이 강조하는 포인트: 작은 예제에서는 차이가 잘 안 느껴진다. 하지만 프로그램이 **크고 복잡해질수록** 체계적 관리가 필수가 되고, 그때 객체지향이 진가를 발휘한다. "개념적으로 이해가 쉽고, 관리가 용이"하다는 게 객체지향을 택하는 이유.

### Stack 설계로 보는 C vs Java

같은 Stack을 두 언어로 설계해 보면 차이가 선명하다.

| | C | Java |
| --- | --- | --- |
| 구조 | **(passive) structure + function** 따로 | **class** (data-fields + methods 한 덩어리) |
| push/pop 호출 | `push(s1, data)`, `pop(s2)` | `s1.push(data)`, `s2.pop()` |
| 데이터 보호 | s1, s2를 **다른 경로로도 마음대로 접근 가능** | object(=data)에 대한 **임의 접근 차단 가능** |

- C에서는 stack 데이터(s1)가 그냥 구조체라서, push/pop 말고 다른 코드가 직접 s1 내부를 건드릴 수 있다.
- Java에서는 data를 class 안에 가두고 method를 통해서만 다루게 만들 수 있다. 이건 단순한 "접근 보호"를 넘어서, **앞으로 계속 나올 캡슐화의 출발점**이다.

→ 결국 이 장의 큰 그림은 **procedure-oriented vs object-oriented**의 대비.

## 2. Visibility Modifiers (접근 지정자)

class 안의 변수·메소드에 누가 접근할 수 있는지를 지정하는 것. 소프트웨어 관리 측면에서 매우 중요하다.

| modifier | 접근 범위 | 한 줄 정리 |
| --- | --- | --- |
| **public** | 모든 package, 모든 class | 제약 없음 |
| **default** (아무것도 안 붙임) | **같은 package** 안에서만 | package로 제약 |
| **private** | **선언된 그 class** 안에서만 | class로 제약 |

세 단계가 점점 좁아지는 구조다: public(전체) ⊃ default(같은 package) ⊃ private(같은 class).

### ⚠️ 객체 변수로 private에 접근하는 문제 (시험 포인트)

여기서 헷갈리기 쉬운 규칙이 있다.

- 다른 곳에서 **객체 변수를 통해**(`obj.field`) private member에 접근하는 건 **불가능**.
- 단, **같은 class 안에서는** private member에 접근 가능 (객체를 통하든 직접이든).

그래서 슬라이드의 질문: **"main()을 같은 class에 두는 게 좋은가?"**
- main을 Circle class 안에 두면 main이 Circle의 private(radius 등)에 막 접근할 수 있다. 당장은 편하지만, 이건 "Circle을 외부에서 일반적으로 쓰는 상황"을 고려하면 좋은 습관이 아니다.
- → **getter/setter를 통해 접근하도록 짜는 게 정석.**

## 3. getter() / setter() (Accessor / Mutator)

private으로 막아 놓은 data에 대해, 외부가 값을 **읽거나(get) 바꿀(set)** 수 있도록 **public 통로**를 열어주는 메소드.

```java
public class Circle3 {
  /** 반지름 — 외부에서 직접 못 건드리게 private */
  private double radius = 1;
  /** 생성된 객체 수 — 모든 객체가 공유(static) */
  private static int numberOfObjects = 0;

  public Circle3() { numberOfObjects++; }
  public Circle3(double newRadius) {
    radius = newRadius;
    numberOfObjects++;
  }

  /** getter: 값을 읽어줌 */
  public double getRadius() { return radius; }

  /** setter: 값을 바꿔줌 + 검증까지 */
  public void setRadius(double newRadius) {
    radius = (newRadius >= 0) ? newRadius : 0;   // 음수면 0으로 막음
  }

  public static int getNumberOfObjects() { return numberOfObjects; }
  public double getArea() { return radius * radius * Math.PI; }
}
```

사용하는 쪽:
```java
Circle3 myCircle = new Circle3(5.0);
// 반지름 10% 키우기
myCircle.setRadius(myCircle.getRadius() * 1.1);   // ⭕ 통로를 통해서
// myCircle.radius *= 1.1;                          // ❌ radius가 private
```

### Why Data Fields Should Be private? (서술형 단골)

1. **data 보호** — 외부가 함부로 못 바꾸게
2. **임의 접근 차단** — class 사용자가 내부를 직접 만지는 것을 막음
3. **유지/보수 용이** — 내부 구현을 바꿔도 getter/setter 인터페이스만 같으면 사용자 코드는 안 바뀜

여기서 **setter의 검증(validation)**이 핵심 이점이다. `setRadius`에서 음수를 0으로 걸러내듯, 직접 접근(`obj.radius = -5`)을 허용했다면 이런 통제가 불가능하다. "값을 바꾸는 유일한 통로"를 메소드로 만들어야 검증을 끼워 넣을 수 있다.

## 4. Package & import

### Package
- 관련된 class/interface를 묶는 **namespace**. 즉 **프로그램 관리 단위**(클래스들을 계층화된 그룹으로 관리).
- 비유: 폴더(디렉토리)로 파일을 계층적으로 관리하는 것과 같다.
- **같은 이름의 class도 소속 package가 다르면 구분된다**: `Project1.Circle`과 `Test.Circle`은 서로 다른 클래스.
- 하나의 package 안에서만 프로그램할 때는 굳이 안 정하고 써도 된다 → **default package**.

### import
- 다른 package(와 그 안의 class)를 쓸 때 선언한다.
```java
import java.util.Date;   // Date 하나만
import java.util.*;      // java.util 안의 모든 것
```

## 5. Passing Objects to Methods

메소드에 인자를 넘길 때 Java는 **항상 pass by value(값 전달)**이다. 단, "값"이 무엇이냐가 타입에 따라 다르다.

- **primitive type**: 값 자체가 복사되어 전달됨. 메소드 안에서 바꿔도 **원본은 안 바뀜**.
- **reference type(object)**: 역시 by value지만, 전달되는 값이 **object를 참조한 값(주소)**이다.
  - → 메소드와 원본이 **같은 객체**를 가리키게 되므로, 메소드 안에서 객체 내용을 바꾸면 **원본도 바뀐다**.
  - 주의: "참조(주소)가 복사"되는 것이지 "객체 자체가 복사"되는 게 아니다.

```java
void m(int x, Circle c) {
  x = 100;             // 호출한 쪽 변수는 안 바뀜 (값 복사)
  c.setRadius(100);    // 호출한 쪽 객체가 바뀜 (같은 객체를 가리킴)
}
```

## 6. Array of Objects

```java
Circle[] circleArray = new Circle[10];
```

- **객체 배열 = 참조 변수의 배열.** 즉 배열의 각 칸은 객체가 아니라 "객체를 가리킬 참조"다.
- `new Circle[10]`만 하면 칸 10개가 생기지만 **각 칸은 아직 `null`**. 그래서 반드시 각 칸을 채워야 한다:
  ```java
  for (int i = 0; i < circleArray.length; i++)
    circleArray[i] = new Circle();
  ```
- `circleArray[1].getArea()`는 **두 단계 참조(two-level referencing)**가 일어난다:
  1. `circleArray` → 배열 전체를 참조
  2. `circleArray[1]` → 그 칸이 가리키는 Circle object를 참조
  3. 그 객체의 `getArea()` 호출

### 응용 — 넓이 합산 (TotalArea)
배열 안 모든 원의 넓이를 더하는 식의 코드가 대표 예제다.
```java
double sum = 0;
for (int i = 0; i < circleArray.length; i++)
  sum += circleArray[i].getArea();
```

## 정리 — 이 장의 핵심 한 줄
> data는 **private**로 숨기고 **getter/setter**라는 통로로만 다룬다(캡슐화). 객체를 메소드에 넘기면 **참조가 전달**되고, 객체 배열은 **참조의 배열**이라 각 칸을 따로 `new` 해야 한다.
