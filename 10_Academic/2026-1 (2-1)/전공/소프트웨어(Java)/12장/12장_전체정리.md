# 12장. Class 2 — 전체정리

> 앞 장들이 "클래스를 어떻게 쓰는가(문법)"였다면, 이 장은 **"객체지향 패러다임으로 문제를 어떻게 풀고, 클래스를 어떻게 잘 설계하는가"**다. 추상화·캡슐화, `this`, 설계 지침 5가지, 그리고 시험에 잘 나오는 **immutable의 함정**이 핵심.

## 1. 클래스 추상화와 캡슐화

- **클래스 추상화(class abstraction)**: 클래스의 **사용**과 **구현**을 분리하는 것.
  - 운전자가 엔진 내부를 몰라도 차를 모는 것과 같다. 어떻게 만들어졌는지(구현)와 어떻게 쓰는지(사용)를 떼어 놓는다.
- **class contract**: 클래스가 "나는 이렇게 쓰면 됩니다"라고 제공하는 설명(메소드 시그니처, 설명). 사용자는 **구현 방법을 몰라도** 이 계약만 보고 쓸 수 있다.
- **class implementation**: 세부 구현은 **캡슐화(encapsulation)**되어 사용자로부터 **숨겨진다**.

→ abstraction(분리) + encapsulation(숨김)이 짝을 이룬다.

## 2. 변수의 scope (영역)

- **instance / static 변수**: 영역이 **class 전체**다. class 안 어디서든 선언할 수 있고, 위아래 순서와 무관하게 클래스 전역에서 보인다.
- **local 변수**: **선언한 위치부터 그 블록 끝까지**만 유효하다.
  - 중요: local 변수는 **사용하기 전에 반드시 명시적으로 초기화**해야 한다. (instance/static처럼 자동으로 0/null이 되지 않는다.)

## 3. this 키워드

`this` = **object 자신**을 가리키는 참조. 두 가지 용도가 핵심이다.

### ① 가려진(hidden) data field 참조
파라미터와 필드 이름이 같으면 필드가 가려진다. `this.`로 "객체 자신의 필드"임을 명시한다.
```java
public Circle(double radius) {
  this.radius = radius;   // this.radius(필드) ← radius(파라미터)
}
```

### ② 같은 class의 다른 constructor 호출
생성자끼리 코드 중복을 줄일 때.
```java
public Circle() {
  this(1.0);   // 위의 Circle(double) 생성자를 호출
}
```
- 단, `this(...)`로 다른 생성자를 부를 때는 **생성자의 첫 문장**이어야 한다.

## 4. Object-Oriented Thinking

- class는 재사용 가능한 소프트웨어를 위해 **유연성(flexibility)**과 **모듈성(modularity)**을 제공한다.
- 절차지향(procedural) vs 객체지향(object-oriented)의 차이: 구성 요소가 많이 등장하는 **대형 프로그램**일수록 절차지향보다 객체지향이 적합하다.
- 강의 예제: **Course(교과목) class**, **StackOfIntegers class** — 데이터와 그에 대한 동작을 한 클래스로 묶어 모델링하는 연습.

## 5. 클래스 설계 지침 (★ 서술형 핵심)

좋은 클래스를 만드는 5가지 원칙. 시험에서 "설계 지침을 설명하라"가 자주 나온다.

### ① 통일성(Coherence)
- **하나의 class는 하나의 entity**만 기술한다. 모든 메소드도 그 entity에 통일되게.
- 예: `Student`는 학생만, `Staff`는 직원만. 둘을 한 클래스로 **합치려 하지 말 것**.
- 공통점이 많다면? 같은 코드가 두 곳에 중복된다 → **상속(inheritance)으로 해결** (13장에서 배움).

### ② 책임 분리(Separating responsibilities)
- 너무 많은 기능을 한 entity에 몰아넣지 말고 **여러 class로 나눈다**.
- 예: `String`(불변), `StringBuilder`(가변), `StringBuffer`(가변+동기화). 셋 다 문자열을 다루지만 책임이 다르다.

### ③ 재사용(Reuse) 가능하게
- 나중에 다양한 **combination/order/environment**에서 통합될 수 있게 설계.
- 특정 목적·생성 순서를 가정하지 말 것. **지나친 최적화 금지** ("이렇게 쓸 거니까 이 정도만"이 나중에 발목을 잡는다).

### ④ 표준 요소 제공
- public **no-arg constructor**
- `equals` method **override**
- `toString` method 제공

### ⑤ 표준 스타일 / 명명 규칙
- 정보를 주는 이름 선택 (변수/메소드 이름만 봐도 역할이 보이게).
- 배치 순서: **data 선언 → constructor → method**.
- 항상 constructor를 제공하고 변수를 초기화해 프로그래밍 오류를 방지.

## 6. Visibility Modifiers — protected의 등장

- 지금까지 본 것: **public / private** (class 내부냐, class 사용자냐의 접근).
- 그런데 클래스는 **상속**되기도 한다. 상속받은 subclass의 접근도 지정해야 한다 → **protected** 등장 (13장에서 본격).
- 원칙은 그대로: private로 데이터를 숨기고, **꼭 필요한 데이터에만** get/set을 제공한다. 사용자가 쓸 일 없는 메소드도 마찬가지로 숨긴다.

## 7. Immutable Objects and Classes (★★ 가장 잘 나옴)

- 한번 만든 객체의 내용이 **변경 불가**하면 **immutable object**, 그 class가 **immutable class**.
- ⚠️ **함정**: "private field만 있고 setter가 없으면 immutable이다" → **틀렸다!**

### 왜 틀렸나 — 예제
```java
public class Student {
  private int id;
  private BirthDate birthDate;          // private, setter 없음
  public Student(int ssn, int y, int m, int d) {
    id = ssn; birthDate = new BirthDate(y, m, d);
  }
  public BirthDate getBirthDate() { return birthDate; }  // 문제의 지점!
}
```
```java
Student student = new Student(111223333, 1970, 5, 3);
BirthDate date = student.getBirthDate();
date.setYear(2010);   // 학생의 생년이 바뀜! → 그래서 mutable
```
- `getBirthDate()`가 **내부 BirthDate 객체의 참조를 그대로 돌려준다.** 외부가 그 참조로 `setYear(2010)`을 부르면 Student 내부 상태가 바뀐다.

### Immutable이 되려면 (3조건)
1. 모든 data field가 **private**.
2. **setter(mutator) 없음**.
3. **변경 가능한 객체에 대한 참조를 리턴하는 accessor도 없어야 함** ← 이 세 번째가 핵심.

→ 검증/보안 검사에서 immutable이 중요하다. 데이터 보호는 결국 **클래스 내부**에서 책임진다.

## 8. static modifier (복습)
- 모든 instance가 공유하는 속성, 개별 객체에 해당하지 않는 속성은 **static**으로 선언한다. (10장과 연결.)

## 9. Top-down? Bottom-up?
- Java 객체지향은 class 하나, method 하나씩 만들다 보면 전체가 완성되는 구조다 → **구현은 Bottom-up이 적합**.
- 단, 문제를 분석하는 단계, 즉 **최상위 수준의 설계는 여전히 Top-down**으로 한다.
- 정리: **설계/분석 = Top-down, 구현 = Bottom-up**.

## 정리 — 이 장의 핵심 한 줄
> 추상화 = **사용/구현 분리**, `this` = 자기 필드·다른 생성자, 설계는 **통일성·책임분리·재사용** 중심. immutable은 **변경 가능한 내부 객체의 참조 반환까지 막아야** 진짜 성립한다.
