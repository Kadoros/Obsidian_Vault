# 18장. Exception Handling — 전체정리

> "에러가 나면 그냥 죽는 프로그램"을 "에러가 나도 살아남거나 우아하게 끝나는 프로그램"으로 만드는 장치. 핵심 질문 두 개: **① 왜 if 대신 예외를 쓰는가, ② 처리를 어디서(발생 지점? 호출자?) 하는가.** 그리고 시험 1순위는 **checked vs unchecked**.

## 1. 왜 예외 처리인가

- program 수행 중 **runtime error**가 나면 program은 **비정상 종료**된다.
- 그런데 **종료되면 안 되는 시스템**이라면? (항공기, 자동차 등 실생활 SW.) program이 계속 실행되거나 적절히 종료되려면, runtime error 같은 **예외 상황을 어떻게 대처할지**가 필요하다.

### if문 처리와 무엇이 다른가
나눗셈에서 0으로 나누는 상황을 보자.
```java
// (a) if로 사전 점검
if (number2 != 0)
  System.out.println(number1 + " / " + number2 + " is " + (number1/number2));
else
  System.out.println("Divisor cannot be zero");

// (b) 예외 처리
try {
  System.out.println(number1 + " / " + number2 + " is " + (number1/number2));
} catch (Exception ex) {
  System.out.println("Exception in division: " + number1 + " / " + number2);
}
System.out.println("Execution continues ...");  // 어쨌든 프로그램은 계속
```

### Exception이 유용한 두 경우 (★)
1. **사전 체크가 여의치 않을 때** — 예: 사용자 입력 오류. 옳은 값이 들어올 때까지 **계속 다시 읽는** 유연한 대처가 가능하다.
   ```java
   do {
     try {
       int number = input.nextInt();
       continueInput = false;
     } catch (InputMismatchException ex) {
       System.out.println("Try again. (정수를 입력하세요)");
       input.nextLine();   // 잘못된 입력 버림
     }
   } while (continueInput);
   ```
2. **runtime error가 호출된 method에서 발생**할 때 — 발생 위치(callee)와 발생 원인(caller)이 **method 경계를 넘어갈 때**. if로 처리하려면 caller? callee? 애매하고, 한쪽 구현 코드가 비공개면 손도 못 댄다.

## 2. Exception의 장점

- method 구현이 exception을 **method의 caller에게 전달(throw)**할 수 있게 해서, 예외 처리를 위로 넘길 수 있다.
- 즉 예외의 발생 원인에 대처하는 게 caller 쪽에서 가능해진다.
- 이 기능이 없다면? method는 **자체 내에서 처리하거나 프로그램을 종료**할 수밖에 없고, 상황에 따른 유연한 처리가 불가능하다.
- 핵심: **method 경계를 넘어 예외 상황을 알릴 수 있다**는 것. (return value와는 **별도의 전달 체계**.)

## 3. 어디서 예외 처리? (두 전략)

### ① method 구현 내에서 직접
- `try/catch`로 **발생 지점과 처리 지점을 한정**한다.
- 장점: 발생 지점에서 직접 처리, try/catch를 한 번만.
```java
try { /* 1 */ } catch { /* 1 */ }
try { /* 2 */ } catch { /* 2 */ }
```

### ② caller에게 위임
```java
int callee() throws Exception { ... }   // throws로 선언
```
- method 정의에 `throws`를 선언하고, **caller 코드에서 try/catch**한다.
- `throws`를 선언 안 해도 (일부 예외는) 위로 처리를 찾아 올라간다. 단 몇몇 exception은 반드시 명시(explicit)해야 한다.
- 장점: **method 구현에 독립적.** 이미 구현된 method에 대해서도 예외처리가 가능하고, **융통성** 있는 처리가 된다. 예외란 본래 unexpected — **정확히 예상 못 한 경우도** 처리할 수 있다.

### 혼용도 가능
- catch해서 **1차 처리 후 다시 throw**(rethrow)할 수 있다.

## 4. Exception Types (계층)

```
Throwable
├── Error  ───────── System errors. JVM이 던짐. 거의 복구 불가
└── Exception
    ├── RuntimeException ── 프로그래밍 오류(bad casting, 배열 범위 초과, 숫자 오류)
    └── 그 외 (IOException 등)
```
- **Error**: internal system error. 거의 발생 안 하고, 나면 user에게 알리거나 프로그램을 적절히 종료하는 수밖에.
- **Exception**: error가 program/외부 환경 때문에 발생. 이건 **program이 처리 가능**.
- **RuntimeException**: 프로그래밍 오류로 인한 것.

## 5. Checked vs Unchecked (★★ 가장 중요)

> 차이의 본질: **compiler가 "이 예외 처리해라"라고 강요하느냐 마느냐.**

- **Unchecked exceptions** = `RuntimeException`, `Error`와 그 subclass들.
  - compiler가 처리를 **강요하지 않음.**
  - 예: NullPointerException(객체 할당 전 참조 접근), IndexOutOfBoundsException(배열 범위 밖 접근).
  - 왜 강요 안 하나? runtime exception은 프로그램 **어디서든 발생 가능**하다. 일일이 try-catch를 강요하면 코드가 try-catch 떡칠이 되니까.
- **Checked exceptions** = 그 외 나머지 전부.
  - 처리 방법을 **반드시 프로그램**해야 한다.

### Catch or Declare (checked 규칙)
callee가 checked exception을 던지면(Error·RuntimeException 제외), caller는 **둘 중 하나**:
- (a) `try-catch` 블록 안에서 호출하거나
- (b) calling method도 그 exception을 **`throws`로 선언**해 위로 넘긴다.

## 6. Declaring / Throwing / Catching (3대 키워드)

### Declaring (선언) — throws
모든 method는 자신이 발생시킬 수 있는 모든 checked exception을 선언해야 한다.
```java
public void myMethod() throws IOException
public void myMethod() throws IOException, OtherException
```

### Throwing (발생) — throw
program이 error를 감지하면, 적절한 exception 인스턴스를 만들어 던진다.
```java
throw new TheException();
// 또는
TheException ex = new TheException(); throw ex;
```
예:
```java
public void setRadius(double newRadius) throws IllegalArgumentException {
  if (newRadius >= 0) radius = newRadius;
  else throw new IllegalArgumentException("Radius cannot be negative");
}
```

### Catching (처리) — try/catch
```java
try { statements; }                      // 예외가 날 수 있는 문장들
catch (Exception1 ex1) { handler1; }
catch (Exception2 ex2) { handler2; }
```
- catch는 **runtime stack을 따라 내려가며(method 경계를 넘어)** catch 블록을 찾아 처리한다.
- Why? 적절한 대응을 위해. callee는 caller의 상황을 모르므로, 처리를 caller까지 올려보내 적합한 곳에서 잡게 한다.

### Rethrowing
```java
catch (TheException ex) {
  perform operations before exits;
  throw ex;                 // 1차 처리 후 다시 던짐
}
```

## 7. finally (★)

```java
try { statements; }
catch (TheException ex) { handling ex; }
finally { finalStatements; }   // 예외 여부와 무관하게 항상 실행
```

흐름을 case별로:
- **예외 없음**: try 끝까지 → finally → next statement.
- **예외 발생 & catch됨**: try 도중 중단 → 해당 catch → finally → next statement.
- **catch에서 rethrow**: try 중단 → catch(rethrow) → **finally 먼저 실행** → 그 다음 제어가 **caller로 이동** (next는 실행 안 됨).

→ 포인트: **finally는 무슨 일이 있어도 실행된다** (파일 닫기, 자원 반납 등에 쓰임).

## 8. Cautions / When to Use

- exception handling은 error 처리 코드를 정상 코드와 **분리**해 프로그램을 읽기·수정하기 편하게 만든다.
- 그러나 새 exception 객체 생성, call stack 되감기, caller로 error 전파 때문에 **시간·자원을 더 쓴다.**

### 언제 try-catch?
- **의도치 않은 error condition**에 쓴다.
- 간단하고 **예상되는 상황엔 쓰지 말 것** — if가 낫다.
```java
// 나쁨: 예상되는 null을 exception으로
try { System.out.println(refVar.toString()); }
catch (NullPointerException ex) { System.out.println("refVar is null"); }
// 좋음: if로
if (refVar != null) System.out.println(refVar.toString());
else System.out.println("refVar is null");
```

### 언제 throw?
- exception을 **caller가 처리하길 원하면** 객체를 만들어 던진다.
- exception이 발생한 그 method에서 다룰 수 있으면 굳이 throw 할 필요 없다.

## 9. Custom Exception Class

- 가능하면 **API에 이미 있는 exception을 쓰는 게 우선.** 부족할 때만 custom.
- `Exception`(또는 그 subclass)을 상속해 만든다.
```java
public class InvalidRadiusException extends Exception {
  private double radius;
  public InvalidRadiusException(double radius) {
    super("Invalid radius " + radius);   // 부모 생성자에 메시지
    this.radius = radius;
  }
  public double getRadius() { return radius; }
}
```

## 10. Assertions

- **assertion** = 추정(assumption)을 확고히 하는 Java 문장. 실행 중 **반드시 true여야 하는 Boolean expression**을 담는다.
- 용도: **program correctness 보장 / logic error 회피**.
```java
assert assertion;                       // 형식 1
assert assertion : detailMessage;       // 형식 2 (메시지 동반)

assert i == 10;
assert sum > 10 && sum < 5 * 10 : "sum is " + sum;
```
- assertion이 **false면 AssertionError가 발생**한다. AssertionError는 Error의 subclass라 메시지를 띄우고 프로그램이 종료된다.
- 기본은 **disable**. 켜려면 `-enableassertions`(또는 `-ea`):
  ```
  java -ea AssertionDemo
  java -ea:package1 -da:Class1 AssertionDemo   // 선택적 on/off
  ```

### Exception vs Assertion (★)
| | 목적 | 범주 |
| --- | --- | --- |
| **Exception handling** | 실행 환경(robustness) 유지 | **robustness** |
| **Assertion** | 추정·내부 일관성/타당성 점검 | **correctness** |
- assertion은 exception handling을 **대체하지 못한다.** 둘은 목적이 다르다.
- assertion은 실행 시점에 검사되고, 프로그램 시작 시 **ON/OFF를 지정**할 수 있다.
- 좋은 활용 예: default가 없는 switch에서 도달하면 안 되는 곳에 `default: assert false : "Invalid month: " + month;`.

## 정리 — 이 장의 핵심 한 줄
> 예외는 **method 경계를 넘어 caller에게 전달**되며(throw/throws), **try-catch**로 잡고 **finally는 항상 실행**된다. **Runtime/Error 계열은 unchecked(강요 X), 나머지는 checked(강요 O).** Exception=robustness, Assertion=correctness.
