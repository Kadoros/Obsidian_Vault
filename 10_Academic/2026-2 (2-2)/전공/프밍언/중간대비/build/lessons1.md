## 언어 개념을 공부하는 이유 {#why}

교안에 6+2개가 나와. 시험에 통째로 나올 확률은 낮지만, 키워드는 알아둬.

- **표현 능력 증가** (Increased ability to express ideas): 아는 언어가 생각의 한계를 정한다. 다른 언어의 기능을 알면 지금 언어에서도 흉내 낼 수 있다.
- **적절한 언어 선택 능력** (Improved background for choosing appropriate languages)
- **새 언어 학습 능력 증가** (Increased ability to learn new languages)
- **구현의 중요성 이해** (Better understanding of significance of implementation): 구현을 알면 언어가 *왜* 그렇게 설계됐는지 보이고, 더 효율적으로 쓴다.
- **이미 아는 언어를 더 잘 쓰기** (Better use of languages already known)
- **컴퓨팅 전반의 발전** (Overall advancement of computing)
- (추가) 언어 설계·컴파일러 구조에 대한 깊은 이해, 코드 유지보수성 향상

> 한 줄 요약(교안 Summary): 다양한 구문을 쓰는 능력↑, 언어를 똑똑하게 고름, 새 언어 배우기 쉬움.

## 프로그래밍 도메인 {#domain}

도메인 ↔ 대표 언어 ↔ 핵심 특징을 한 세트로 외우면 돼.

| 도메인 | 대표 언어 | 특징 |
|---|---|---|
| 과학 응용 (Scientific) | **Fortran** (FORmula TRANslation) | 대량의 부동소수점 계산, 배열 |
| 사무 응용 (Business) | **COBOL** | 보고서 생성, 십진수·문자 처리 |
| 인공지능 (AI) | **LISP** (LISt Processing) | 숫자보다 기호(symbol) 처리, 연결 리스트, 코드=데이터(homoiconicity) |
| 시스템 프로그래밍 | **C** | 계속 실행되므로 효율이 중요 |
| 웹 소프트웨어 | HTML, PHP, Java 등 | 마크업 + 스크립팅 + 범용 언어의 잡다한 조합 |

> 함정: LISP의 핵심은 "기호 처리 + 리스트". 수치 계산 = Fortran, 십진수 = COBOL.

## 언어 평가 기준 4가지 {#criteria}

| 기준 | 한글 | 한 줄 정의 |
|---|---|---|
| Readability | **판독성** | 프로그램을 얼마나 쉽게 읽고 이해할 수 있나 |
| Writability | **작성력** | 주어진 도메인의 프로그램을 얼마나 쉽게 작성할 수 있나 |
| Reliability | **신뢰성** | 모든 조건에서 명세대로 동작하나 (conformance to specifications) |
| Cost | **비용** | 교육·작성·컴파일·실행·유지보수 등의 총비용 |

> 시험 포인트: 24 중간 1번이 정확히 "평가 기준 4가지와 각 기준을 간략히". 정의 한 줄씩만 쓰면 3점.

교안 표(p.9)의 관계: **단순성, 직교성, 데이터 타입, 구문 설계**는 판독성·작성력·신뢰성에 모두 영향. **추상화 지원, 표현력**은 작성력·신뢰성. **타입 검사, 예외 처리, 제한된 별칭**은 신뢰성만.

## 판독성이 왜 중요해졌나 {#read-why}

- 유지보수가 SW 생명주기의 큰 부분으로 인식됨 → 유지보수 용이성은 판독성이 좌우.
- 관점이 **기계 중심 → 사람 중심**으로 바뀜.
- 판독성은 그 언어의 문제 도메인 맥락에서 판단해야 한다.

## 전반적 단순성 (Overall simplicity) {#simplicity}

기능·구조가 적은 언어가 읽기 쉽다. 단순성을 해치는 두 가지:

- **특징 다중성** (feature multiplicity): 같은 일을 하는 방법이 여러 개.
  예) `cnt = cnt + 1;` `cnt += 1;` `cnt++;` `++cnt;`
- **연산자 중복** (operator overloading): 하나의 연산자 기호가 여러 의미.

## 직교성 (Orthogonality) {#orthogonality}

**적은 수의 기본 구조를 조합한 모든 경우가 합법적이고 의미가 있는 성질.**
직교성↑ → 규칙의 예외↓ → 규칙성↑ → 배우기·읽기 쉬움.

C의 비직교적 예:
- 구조체(record)는 함수에서 반환할 수 있지만 배열은 못 한다.
- 배열 원소는 void나 함수를 제외한 모든 타입이 될 수 있다.

직교적 예: VAX의 `ADDL op1, op2` (피연산자가 레지스터든 메모리든 다 됨).

**너무 많은 직교성도 문제**: 모든 것이 값을 갖는 식이 되면
```
x := (if a > b then a := b else b := a fi);
```
같은 이상한 조합도 합법이 되어 오히려 읽기 어렵고, 오류가 안 잡힌다.

> 시험 포인트: "직교성이란?" → "적은 기본 구조들의 모든 조합이 합법적이고 의미 있음" + C 배열 반환 불가 예.

## 데이터 타입과 구문 설계 {#syntax-design}

**데이터 타입**: 타입·자료구조를 정의할 충분한 장치가 있으면 읽기 쉽다.
예) Boolean이 없으면 `timeOut = 1` (뭔 뜻?) vs `timeOut = false` (명확). C89엔 bool이 없었고 C99의 `stdbool.h`에서 생김.

**구문 설계**가 판독성에 주는 영향 3가지:
- **특수어** (special words): `while`, `for` 같은 단어. 복합문 형성 방법도 포함 (C는 `{}`, Ada는 `end if`, `end loop` → Ada가 더 읽기 쉬움).
- **형식과 의미** (form and meaning): 의미가 형식(구문)에서 바로 드러나야 한다.
  반례: C의 `static`은 위치에 따라 의미가 다르다. 함수 안 → 컴파일 시간에 생성(호출마다 새로 안 생김). 함수 밖 → 그 파일에서만 보임.

## 작성력 (Writability) {#writability}

판독성에 영향 주는 특성 대부분이 작성력에도 영향. 도메인 맥락 중요.

- **단순성과 직교성**: 적은 기본 구조 + 적은 조합 규칙. 장점: 단순한 집합만 배우면 됨. 단점: 직교성이 너무 크면 오류가 탐지 안 됨.
- **추상화 지원**: 세부를 무시하고 복잡한 구조를 정의·사용.
- **표현력** (Expressivity): 강력한 연산자로 작은 프로그램이 많은 계산을 함. 예) APL의 `A+.×B`, C의 `count++`가 `count = count + 1`보다 편함.

## 신뢰성 (Reliability) {#reliability}

모든 조건에서 명세대로 수행하면 신뢰성이 있다. 영향 주는 특성:

- **타입 검사** (type checking): 오류는 일찍 발견할수록 고치는 비용이 싸다. 컴파일 시간 검사 > 실행 시간 검사. Java는 거의 모든 변수·식의 타입을 컴파일 시간에 검사.
- **예외 처리** (exception handling): 실행 시간 오류를 가로채 시정 조치.
- **별칭** (aliasing): 같은 메모리 위치를 두 개 이상의 이름(참조 방법)으로 접근 → 신뢰성 저하.
- **판독성과 작성력**: 읽고 쓰기 쉬울수록 맞게 짤 가능성이 높다.

> 함정: "별칭"은 신뢰성을 *낮추는* 요인. 별칭 = 같은 메모리 셀에 대한 둘 이상의 참조 방법.

## 비용 (Cost) {#cost}

1. 프로그래머 교육 비용
2. 프로그램 작성 비용
3. 컴파일 비용
4. 실행 비용 (최적화 정도와 trade-off)
5. 언어 구현 시스템 비용
6. 신뢰성 부족에 따른 비용 (예: 핵발전소, Mars Pathfinder 우선순위 역전)
7. **유지보수 비용** (수정 + 기능 추가)

## 기타 기준 {#other-criteria}

- **이식성** (Portability): 한 구현에서 다른 구현으로 옮기기 쉬움. 표준화 정도가 가장 큰 영향.
- **일반성** (Generality): 넓은 범위의 응용에 적용 가능.
- **분명성** (Well-definedness): 공식 정의의 완전성과 정밀성.

## 언어 설계에 영향을 준 두 요인 {#influences}

1. **컴퓨터 구조** (폰 노이만 구조) → **명령형 언어**
2. **프로그래밍 설계 방법론** → 새 패러다임

**폰 노이만 구조**: 데이터와 프로그램이 같은 메모리에, 메모리는 CPU와 분리, 명령어·데이터가 메모리→CPU로 파이프됨.
명령형 언어와의 대응:
- **변수** ↔ 메모리 셀
- **배정문** ↔ 파이핑(데이터 이동)
- **반복** 이 효율적 (명령어가 인접 메모리에 있으므로)

**폰 노이만 병목**: 메모리↔CPU 버스 전송 속도가 명령 실행 속도보다 느려서 컴퓨터 속도의 주된 제한 요인이 됨.

**Fetch-execute cycle**:
```
initialize the program counter
repeat forever
    fetch the instruction pointed by the counter
    increment the counter
    decode the instruction
    execute the instruction
end repeat
```

**방법론 변화**: 1950s~60s 초 기계 효율 → 60s 후반 사람 효율(구조적 프로그래밍, 하향식 설계, 단계적 세분화) → 70s 후반 절차 지향→**데이터 지향**(데이터 추상화) → 80s 중반 **객체 지향**(데이터 추상화 + 상속 + 다형성/동적 바인딩).

## 언어 범주 {#categories}

| 범주 | 핵심 | 예 |
|---|---|---|
| 명령형 (Imperative) | 변수, 배정문, 반복. OOP·스크립트·비주얼 언어 포함 | C, Java, Perl, JavaScript, C++ |
| 함수형 (Functional) | 주어진 매개변수에 함수를 적용해 계산. **불변성, 순수 함수** | LISP, Scheme, ML, F# |
| 논리형 (Logic) | 규칙 기반, 규칙에 특정 순서가 없음 | Prolog |
| 마크업/프로그래밍 혼합 | 마크업 언어에 프로그래밍 기능 일부 추가 | JSTL, XSLT |

> 함정: 객체지향 언어와 스크립트 언어는 별도 범주가 아니라 **명령형에 포함**.

## 언어 설계 절충 (Trade-offs) {#tradeoffs}

"상충하는 기준을 절충하는 것이 주요 공학 과제" (Hoare). 교안의 3쌍과 예:

| 상충 | 예 |
|---|---|
| **신뢰성 vs 실행 비용** | Java는 모든 배열 참조의 인덱스 범위를 검사 → 신뢰성↑ 실행 비용↑ |
| **판독성 vs 작성력** | APL은 강력한 연산자·새 기호가 많아 짧게 쓰지만(작성력↑) 읽기 어려움(판독성↓) |
| **작성력(유연성) vs 신뢰성** | C++ 포인터는 강력·유연하지만 신뢰성이 낮음 |

## 구현 방법 3가지 {#impl-methods}

| 방법 | 핵심 | 속도 | 용도 |
|---|---|---|---|
| **컴파일** (Compilation) | 고급 언어 → 기계어로 번역 (JIT 포함) | 번역 느림, **실행 빠름** | 대형 상용 응용 |
| **순수 해석** (Pure interpretation) | 번역 없이 인터프리터가 직접 해석·실행 | 실행 10~100배 느림, 공간 더 필요 | 작은 프로그램, 효율이 중요치 않을 때 |
| **혼합형** (Hybrid) | 중간 언어로 번역 후 그것을 해석 | 순수 해석보다 빠름 | 효율이 최우선이 아닌 중소 시스템 |

> 시험 포인트: 24 중간 3번 = "세 가지 방법과 각각 간략히". 위 표의 "핵심" + 속도 특징 한 마디.

## 컴파일 과정 {#compile-phases}

```
원시 프로그램 → [어휘 분석기] → 어휘 단위들
              → [구문 분석기] → 파스 트리
              → [중간 코드 생성기 + 의미 분석기] → 중간 코드
              → (최적화) → [코드 생성기] → 기계어
   (모든 단계가 심볼 테이블을 참조)
```

- **어휘 분석** (lexical analysis): 문자 → 어휘 단위(lexical units)
- **구문 분석** (syntax analysis): 어휘 단위 → 파스 트리 (구문 구조)
- **의미 분석**: 중간 코드 생성 (타입 오류 등 검사)
- **코드 생성**: 기계어 생성

용어:
- **링킹과 적재** (linking and loading): 시스템 프로그램(라이브러리)을 모아 사용자 프로그램(목적 코드)에 연결하는 과정.
- **적재 모듈** (load module, executable image): 링킹 결과물로 실행을 위해 메모리에 적재되는 것.

## 순수 해석 · 혼합형 · JIT {#interp-hybrid}

**순수 해석**: 번역 없음. 실행 시간 오류를 즉시 소스 수준에서 보여주기 쉬움. 느리고 공간이 더 필요. 전통 고급 언어에선 드물지만 웹 스크립트(JavaScript, PHP)로 부활.

**혼합형**: 고급 언어 → 해석하기 쉬운 **중간 언어**로 번역 → 해석.
- Perl: 해석 전에 부분 컴파일해 오류 탐지.
- 초기 Java: 중간 형태 = **바이트 코드**. 바이트코드 인터프리터 + 런타임 시스템 = **JVM** → 이식성.

**JIT (Just-in-Time)**: 먼저 중간 언어로 번역 → 부프로그램이 **호출될 때** 그 중간 코드를 기계어로 컴파일 → 기계어 버전은 이후 호출을 위해 보관. Java, .NET이 사용. 본질적으로 **지연된 컴파일러** (delayed compiler).

## 전처리기와 프로그래밍 환경 {#preproc-env}

**전처리기** (preprocessor): 컴파일 직전에 프로그램을 처리해 내장된 전처리기 매크로를 확장.
- `#include "myLib.h"` → 그 위치에 파일 내용을 복사
- `#define max(A, B) ((A) > (B) ? (A) : (B))`
