Data Model and Abstraction
q What is a Data Model?
  ■ A collection of concepts that describe the structure of a database
  ■ Providing the necessary “Tools” to achieve data abstraction
    q e.g., data types, relations, and constraints that apply to the data
    q e.g., basic operations for specifying retrievals and updates on the DB

                                                                                      for understanding of data

Data Independence
q What is the Data Independence?
  ■ The capacity to change the schema at one level of a database system without
    having to change the schema at the next higher level

                                                                    What if we change the conceptual schema?
                                                                    E.g., adding a new data or removing a data


                                                                Logical Data Independence
                                                               à The Capacity to Change the Conceptual Schema

                                                               Physical Data Independence
                                                               à The Capacity to Change the Internal Schema
                                                                 What if we change the physical storage organization?
                                                               (e.g., providing an access path to improve retrieval speed)



                Significantly reduces the maintenance overhead of existing application programs

Categorization of Attributes
q Category 1: Composite vs Simple Attributes
  ■ Composite attributes: can be divided into smaller subparts
     q   e.g., Address consists of Street_address, city, state, and zip
  ■ Simple (atomic) attributes: non-divisible
     q   e.g., city, state, zip, number, street, apartment_number

q Category 2: Single-Valued vs Multivalued Attributes
  ■ Single-valued attributes: have a single value for a particular entity
     q   e.g., (most attributes) age, gender, birth date, SSN, …
  ■ Multivalued-valued attributes: have a set of values for the same entity
     q   e.g., phone numbers, college degrees, …
q Category 3: Stored vs Derived Attributes
  ■ Stored attributes: actually stored in the database
     q   e.g., birth date
  ■ Derived attributes: not stored in the database, but can be derived from others
     q   e.g., age (derived from the birth date)

Constrains on Relationship Types
q Why Constraints of a Relationship Type Need?
  ■ Relationship types usually have certain constraints about participating entities
     q e.g., each employee must “work for” exactly one department
     q e.g., each employee can “work on” multiple projects and should be “supervised” by exactly one employee


q Types of Constraints
  ■ Constraint 1: Cardinality Ratio
     q To specify the maximum number of relationship instances that an entity can participate in
     q Three types of cardinality ratios for a binary relationship: 1:1, 1:N, M:N

  ■ Constraint 2: Participation Constraint
     q To specify whether the existence of an entity depends on its being related to another entity
     q Two types of a participation constraint
        § Total: every entity should participate in the relationship
        § Partial: every entity does not need to participate in the relationship


                                                                                                         26
Constraint 1: Cardinality Ratio
q 1:N Cardinality Ratio
  ■ A 1:N binary relationship relates an entity to any number of entities

Weak Entity Types
q What is a Weak Entity Type?
  ■ An entity type has no key attributes of its own inside the entity type
  ■ A weak entity type depends on its identifying entity type
     q   Each weak entity must be associated with an identifying entity

q Identifying Relationship
  ■ Relating a weak entity type to its owner entity type
  ■ A weak entity type always has a total participation constraint
