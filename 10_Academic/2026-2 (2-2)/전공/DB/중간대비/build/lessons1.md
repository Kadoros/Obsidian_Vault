## DB, DBMS, DB 시스템 {#db-def}

| 용어 | 정의 |
|---|---|
| **Database (DB)** | 논리적으로 일관된(logically coherent), 서로 관련된 데이터의 모음. DBMS가 관리한다 |
| **DBMS** | 데이터를 구조화된 방식으로 효율적으로 "관리"하는 소프트웨어. DB를 **정의(defining), 구축(constructing), 조작(manipulating), 공유(sharing)** 한다. 예) IBM DB2, Oracle, MS SQL Server, MySQL, SQLite |
| **Database System** | **DB + DBMS 소프트웨어** |

> 시험 포인트: DBMS의 기능 4가지 동사(define, construct, manipulate, share)와 "DB 시스템 = DB + DBMS"를 짝으로.

## 왜 DBMS를 쓰나 {#why-dbms}

교안 예: 메시지 앱 데이터(친구 정보, 메시지)를 **텍스트 파일**에 한 줄씩, 쉼표로 속성을 나눠 저장하면 생기는 문제 세 묶음.

- **데이터 무결성 (Data Integrity)**: 메시지 길이 제한을 어떻게 지키나? 친구 정보를 실수로 중복 입력하면? 이름이 같은 친구는?
- **데이터 관리 (Data Management)**: 특정 메시지를 빨리 찾으려면? 여러 사용자가 동시에 읽고 쓰면?
- **데이터 지속성 (Data Durability)**: 앱이 쓰는 도중에 기계가 죽으면? 크래시 후 복구는?

→ 이런 기술 문제를 매번 직접 풀 수 없으니 DBMS를 쓴다. 응용 예: 전자상거래, 은행, SNS, 대학/도서관, 항공·철도 예약.

## DBMS를 쓰지 않는 게 나을 때 {#when-not}

**DBMS의 오버헤드**
- 하드웨어·소프트웨어·교육에 드는 **높은 초기 투자**
- 데이터를 정의·처리하는 **범용성(generality)** 자체의 비용
- 보안, 동시성 제어, 회복, 무결성 기능의 부담 → "너무 무겁다"

**맞춤형(customized) DB가 나은 경우**
- 단순하고 잘 정의되어 **절대 바뀌지 않을** 응용 (추가·삭제·갱신이 없음)
- DBMS로는 맞출 수 없는 **엄격한 실시간 요구**
- 저장 용량이 제한된 **임베디드 시스템**
- **다중 사용자 접근이 없음**

## 1) 자기 기술성 (Self-Describing Nature) {#self-desc}

DB 시스템은 DB 자체뿐 아니라 **메타데이터**도 담고 있다.
- **메타데이터**: DB 구조와 제약조건의 정의
- 메타데이터는 **DBMS 카탈로그(catalog)** 에 저장된다. DB를 유지하는 데 꼭 필요하다
- 정의하는 방법 = SQL DDL (4–5주차)

> 함정: 메타데이터가 저장되는 곳은 "카탈로그". 파일 시스템은 데이터 구조 정의가 응용 프로그램 안에 박혀 있다.

## 2) 데이터 추상화 (Data Abstraction) {#abstraction}

**프로그램과 데이터 사이의 절연 (insulation between programs and data)**
- DB 시스템은 데이터의 **개념적 표현(논리 수준)** 을 제공한다: 객체, 속성, 상호 관계
- 복잡한 **물리 수준** 구조(저장 방식, 연산 구현)는 드러내지 않는다
- 데이터 구조가 바뀌어도 프로그램은 영향을 받지 않는다 → **프로그램-데이터 독립성 (program-data independence)**

## 3) 다중 뷰 지원 (Support of Multiple Views) {#multi-views}

사용자마다 필요한 데이터 관점이 다르다.
- **뷰 (view)**: DB에서 파생됐지만 **명시적으로 저장되지 않은 가상 데이터**
- 사용자는 그 데이터가 저장된 것인지 파생된 것인지 몰라도 된다
- 예) 대학 DB에서 뷰 1 = 학생별 성적표 출력, 뷰 2 = 과목별 선수과목 확인

## 4) 데이터 공유와 다중 사용자 트랜잭션 처리 {#sharing}

- 여러 사용자가 **동시에** DB에 접근. 여러 앱의 데이터를 하나의 DB에 통합해 관리
- 예) 좌석이 하나 남은 항공편에 예약 담당자 여러 명이 동시에 배정하려는 상황
- **동시성 제어 (concurrency control)** 가 필요
- **트랜잭션 (transaction)**: 하나의 논리적 기능을 수행하는 연산들의 모음
- 트랜잭션은 **ACID** 를 만족해야 한다: **A**tomicity(원자성), **C**onsistency(일관성), **I**solation(고립성), **D**urability(지속성) → 14주차

> 시험 포인트: 특징 4가지 이름을 영어로 정확히 + 각각 한 줄. "self-describing / data abstraction / multiple views / sharing & multiuser transaction processing".

## 데이터 모델 3가지 범주 {#data-models}

**데이터 모델**: DB 구조를 기술하는 개념들의 모음. 데이터 추상화를 위한 "도구" (데이터 타입, 관계, 제약조건, 검색·갱신 연산).
- 추상화 = 데이터 이해에 필요한 본질은 강조하고, 데이터 조직·저장의 세부는 감추는 것

| 범주 | 수준 | 내용 |
|---|---|---|
| **개념적 (conceptual)** | high-level | 사용자가 데이터를 인식하는 방식에 가까운 개념. 예) ER 모델 (EMPLOYEE, DEPARTMENT, PROJECT) |
| **표현적 (representational)** | 중간 | DBMS가 데이터를 관리하는 방식. 물리 저장 세부는 숨기지만 컴퓨터에 바로 구현 가능. 예) 관계 데이터 모델 |
| **물리적 (physical)** | low-level | 데이터가 컴퓨터에 저장되는 방식: 레코드 형식, 순서, 접근 경로. 일반 사용자가 아니라 전문가용 |

## 3단계 스키마 구조 (Three-Schema Architecture) {#three-schema}

**목표: 사용자 응용을 물리적 DB에서 분리** → 사용자 프로그램과 데이터의 독립.

| 수준 | 스키마 | 기술하는 것 |
|---|---|---|
| **외부 (external)** | 외부 스키마 / 사용자 뷰 | 특정 사용자 그룹이 관심 있는 DB 구조의 일부 |
| **개념 (conceptual)** | 개념 스키마 | 전체 DB의 논리 구조. **표현적 데이터 모델**로 기술. 엔티티, 데이터 타입, 관계, 연산, 제약조건. 물리 저장 구조는 숨김 |
| **내부 (internal)** | 내부 스키마 | DB의 물리 저장 구조. **물리적 데이터 모델**로 기술. 저장·접근 경로의 세부 |

> 함정: 실제 데이터는 **물리(내부) 수준에만** 저장된다. 외부·개념 스키마는 "기술"일 뿐.

## 스키마 간 사상 (Mapping) {#schema-mapping}

실제 데이터는 내부 수준에만 있으니, DBMS가 요청과 결과를 수준 사이에서 **변환**해야 한다.
- 요청: 외부 스키마 → 개념 스키마 → 내부 스키마로 바꿔서 저장된 DB에서 처리
- 결과: 저장된 DB에서 꺼낸 데이터를 사용자의 외부 뷰에 맞게 다시 형식화
- **사상 정보도 카탈로그에 저장된다**

## 데이터 독립성 (Data Independence) {#data-indep}

**한 수준의 스키마를 바꿔도 바로 위 수준의 스키마를 바꿀 필요가 없는 능력.**

| 종류 | 바꾸는 것 | 예 |
|---|---|---|
| **논리적 데이터 독립성** | **개념 스키마** | 새 데이터 추가, 데이터 제거 → 외부 스키마·응용 프로그램은 그대로 |
| **물리적 데이터 독립성** | **내부 스키마** | 저장 구조 변경, 검색 속도를 위해 접근 경로(인덱스) 추가 → 개념 스키마 그대로 |

→ 기존 응용 프로그램의 **유지보수 부담을 크게 줄인다**.

> 시험 포인트: "논리 = 개념 스키마 변경, 물리 = 내부 스키마 변경"을 섞지 마. 물리적 독립성이 더 달성하기 쉽다 (인덱스 추가는 흔한 일).
